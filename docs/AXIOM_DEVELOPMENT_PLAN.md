# AXIOM 完整开发计划

本计划以[简历目标稿](AXIOM_RESUME.md)为最终交付目标，以 [WP-04 验收记录](AXIOM_VALIDATION.md)为当前基线。机器学习是第一个场景。内环优化实验候选，外环优化 Harness 的运行策略。每个阶段以可运行的演示、回归用例和验收记录结项。

## 架构与数据边界

| 层 | 交付边界 |
| --- | --- |
| Pi 运行时 | 复用 Pi Agent SDK 的 Session 与工具扩展，沿用 CLI/RPC、模型请求和通用上下文压缩。Pi Durable 提供任务检查点、持久化调度及重放语义。Pi 已提供的能力按复用说明。[Pi CLI](../packages/coding-agent/README.md) · [Pi SDK](../packages/coding-agent/docs/sdk.md) · [Pi Durable](../packages/durable/README.md) |
| AXIOM 实验控制 | 审批 TaskSpec，持久化实验身份、状态、预算和结果，调用执行器与独立评估器。任务恢复与选优由领域证据判定。每类业务状态只有一处权威来源。 |
| 执行器与领域适配 | 执行器负责启动、查询、取消、退出状态和产物收集。领域适配器定义候选空间、分级评估协议、指标和可交付内容。先接现有 Tiny CPU，再接 OCI 容器与 Slurm。 |
| 评测与策略优化 | AXIOM-Bench 分别判定任务是否达成和运行机制是否符合规则。外环消费开发轨迹，独立评测控制策略发布。评分器、权限边界与留出数据由运行方控制。 |

两类优化都记录候选身份与策略版本。内环候选是实验代码或参数，外环候选是可审查的 Harness 配置变更。首版策略版本仅包含受限配置，已有任务始终绑定其启动时的版本。

## 实施顺序

### 1. P0 · WP-05 持久执行

- **先验证运行时接入。** 用本仓库的 Pi Durable 和 SQLite 证明一个扩展任务可持久化、重新打开并读取检查点。确认存储单写者约束以及与现有启动器的连接方式。用架构记录固定入口、SQLite 事务边界、状态权威和重放策略，再接入现有 Tiny CPU。
- **实现实验账本。** 写入前后均使用稳定的任务 ID、运行 ID、操作 ID。先在同一事务登记执行意图和预算预留，再启动训练或请求模型。完成后记录实际用量、独立评估及产物摘要。候选指纹绑定规范化结构、配置、可信输入和评估协议，同一次恢复沿用原 TaskSpec 和绝对截止时间。
- **实现恢复与交付。** 第二个实例不能接管仍被占用的存储。已核验的操作复用结果；已记录意图但外部执行无法确认时挂起并保留预留。将证据损坏和外部状态未知分开报告。可继续交付经独立核验的历史最佳。旧 WP-04 记录可继续查阅，新恢复入口只接受具备必要字段的任务。
- **确定 Checkpoint 口径。** WP-05 保存和恢复 Harness 的任务检查点。PyTorch 模型权重作为产物独立重载。Slurm 重接验证的是继续监控原作业。训练进程本身中断后的训练步级续跑需要模型、优化器等训练状态和单独的验收记录。
- **验收。** 在基线和首轮完成后强制结束进程，再打开同一任务执行剩余候选。同一任务 ID、原截止时间、预算计数和已有产物哈希一致。真实启动记录证明基线及首轮未重跑。覆盖启动前后崩溃、用量未知、并发恢复、证据损坏、截止到期及用户取消。首版验收范围为单机进程恢复，主机掉电与 Slurm 恢复分别验证。

### 2. P0 · 自主科研搜索与 AXIOM-Bench

- **实现搜索。** 起步沿用可信 Tiny CPU 的模型结构约束，再增加由 TaskSpec 审批的超参数白名单和取值范围，分别验证结构与学习率等参数的搜索。每轮记录假设、支持假设的上一轮证据、候选差异和下一步决策。候选依次经过静态校验、Smoke、低成本 Proxy 和完整评估，记录去重、剪枝、晋级理由及每阶段成本。只用完整独立评估进入最终 Pareto 集，计算质量与执行成本的取舍，按用户偏好选交付物。
- **建立最小评测集。** 先将 WP-05 故障注入与现有终止、越权、去重、候选退化回归整理成带固定输入、预期状态和独立评分器的案例。引入多保真策略后，在相同候选池、资源和协议下对照现有全训策略，记录 Proxy 淘汰优质候选的情况。
- **验收。** 至少完成一组预算内对照，输出候选轨迹、完整训练次数与成本、独立指标及 Pareto 选择。结构和超参各有一条可追溯的反馈迭代轨迹，超参越界须在执行前被拒绝。故障案例分别判任务达成与 Harness 正确性。每条归因链接事件、命令或产物，缺少证据时归为未知。CI 先使用 faux provider 与固定 CPU 用例。真实模型评测在同一模型、用例和预算下重复多轮，报告任务成功率、`pass@k`、`pass^k`、恢复成功率、重复作业数、实际 Token、越权拦截和独立复验，公开各项计数及样本范围。

### 3. P1 · 上下文、执行治理与证据链

- **上下文。** 工作窗口只接收当前任务与近轮反馈，结构化状态保存预算、候选和进展，经验层检索相似实验或失败，原始日志和权重留在产物层。上下文包里使用摘要与产物引用，并保留终止原因、错误诊断和关键指标。
- **执行治理。** TaskSpec 固定工具、可写路径、网络和资源。审批记录绑定 TaskSpec 版本与授权资源，未审批或超出审批范围的操作不得启动。工具准入与执行器共同执行约束，候选运行在受限 Docker 环境，评分器单独持有留出输入。策略配置附有 Schema 和可变字段白名单，评分器、权限边界及评测数据由运行方维护。
- **证据链。** 用运行 ID 串起模型决策、执行记录、评分与交付。Run Manifest 记录代码、依赖、数据、策略、评估器和产物摘要。OpenTelemetry 导出运行轨迹，MLflow 展示实验指标与产物。实验判定以账本与独立评分为准。
- **验收。** 同一任务用完整日志和分层上下文做对照，报告实际输入 Token、关键错误是否留存，以及重启后能否沿用正确状态继续决策。验证拒绝审批时启动次数为零、越权拒绝、资源超限取消和留出集隔离。用产物清单复算一组结果，从 Run Manifest 的 run ID 核对 OpenTelemetry 轨迹和 MLflow 的同一次评分与产物。

### 4. P1 · 自进化 Harness

- 从一类可重复故障出发，首选训练工具输出策略。外环读取归因后的开发轨迹，提出受限配置变更，并记录假设、变更差异和所针对的案例。被拒绝后，外环读取开发集上的失败证据并提出修订，验证第二轮策略是否解决前一轮问题。留出集明细不进入后续候选上下文。
- 用同一模型、任务、预算和评分协议比较当前策略与候选。发布门槛先固定，至少覆盖任务成功率、关键错误可诊断性、预算和安全回归。开发轨迹用于提出和筛选候选，隔离留出集用于发布判定。
- **验收。** 展示一条通过门槛后发布的策略，以及一条被回归门槛拒绝的策略。报告含基线、候选、原始计数、负例和版本变更。发布后新任务加载新版本，运行中的任务继续使用原版本。回滚后新任务恢复上一已验收版本。

### 5. P2 · 扩展领域任务与远程算力

| 交付 | 主要工作 | 验收证据 |
| --- | --- | --- |
| RAG 检索优化 | 固定可分发语料与相关性标注，以 BM25 为基线，逐步接入 Qdrant 向量召回、融合和重排。用同一实验控制层搜索分块或排序参数。 | 开发集用于选优，留出集独立复算 Recall@K、nDCG@K。报告保留索引版本、查询级指标和质量与延迟的取舍。 |
| 消融与论文复现 | 用种子和控制变量展开实验矩阵，复用同条件历史结果。按 Run / Evaluate / Train 表达复现深度，记录依赖、数据、模型和指标口径。 | 在可公开任务上独立重跑关键对照，并用可追溯报告定位论文设定与结果差异。DETR 量化可作为后续多目标测试任务。 |
| Slurm GPU | 保存本地提交意图和远程作业 ID，断连后按提交标识查询排队、运行及终态。提交状态未知时暂停重发。将预算、取消、日志复查和产物收集接到远端。 | 实际提交一个 GPU 作业，杀掉本地进程再恢复监控。对账证明只提交一次，并验证取消或正常退出及产物可核验。 |

### 6. P3 · 管理界面

账本与报告格式稳定后，再用只读界面展示运行状态、预算、评测对照和产物链接。验收以状态和统计与 CLI 报告一致为准。

## 简历主张与验收映射

| 简历亮点 | 对应阶段 | 完成后可提供的证明 |
| --- | --- | --- |
| 自进化 Harness | 第 2、4 阶段 | 一条从历史失败轨迹到归因、策略提案、反思修订、独立回归、版本发布及回滚的完整链路。 |
| 持久化执行引擎 | 第 1、5 阶段 | 同一任务重启后沿用预算和检查点的本地演示，加上同一 Slurm GPU 作业的断连重接和无重复提交证据。 |
| 自主科研优化 | 第 2、5 阶段 | 模型结构、超参和 RAG 各有独立运行记录。能查到假设、先前反馈、多保真剪枝、完整评分与 Pareto 选优结果。 |
| 上下文工程 | 第 3 阶段 | 四层上下文重建轨迹，以及同任务输入 Token 和恢复连续性的对照记录。 |
| 安全执行与工具治理 | 第 3、4 阶段 | TaskSpec 审批及工具决策记录、Docker 限制与评估隔离测试、外环策略越权拒绝用例。 |
| Agent Evals 与可观测性 | 第 2、3、4 阶段 | AXIOM-Bench 评分卡、失败归因证据、相互可定位的 OpenTelemetry 轨迹与 Run Manifest，以及独立复验结果。 |

**技术栈核对。** TypeScript、Node.js、Pi Agent SDK 对应运行入口与扩展，Python 和 PyTorch 对应现有训练与独立评估。Pi Durable、SQLite 对应第 1 阶段，Docker、OpenTelemetry、MLflow 对应第 3 阶段，Slurm、Qdrant 对应第 5 阶段。每项新增技术须有可运行的集成和验收记录后，才计入已完成技术栈。

## 发布与验收规则

- **保住现有基线。** 涉及实现的阶段按仓库要求跑 `npm run check`、相关定向测试和 `npm run test:ml`，需要编译产物时先构建。交互 TUI 验收单独记录。数据、费用或硬件条件未满足时，把相应阶段标记为待验收。
- **记录可核对的结果。** 每阶段保存提交版本、样例输入、运行方式、退出状态、原始计数、指标、产物及其验证方式。持久化阶段以实际进程记录核对是否重复启动。评测报告分别呈现任务完成、可靠性、资源、规则与复验结果。
- **用证据更新简历。** 完成一个阶段后，将能力、测试范围和结果追加到[验收记录](AXIOM_VALIDATION.md)，再核对[简历目标稿](AXIOM_RESUME.md)的对应主张。参考研究与当前实现范围见[路线图](AXIOM_ROADMAP.md)。
