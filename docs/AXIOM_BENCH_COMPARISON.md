# WP-07.2 · AXIOM-Bench 真实 Agent 对照

## 对照组

| 组 | Pi 运行方式 | 科研控制 |
| --- | --- | --- |
| B0 | 原生 Pi RPC、原生 Tool Calling、四个受控工具 | 直接调用共享执行器。工具返回固定 baseline 和最近候选反馈。交付最后一个有效候选。 |
| B1 | 与 B0 相同的 Pi 入口、工具、审批和计算配额 | 增加历史摘要以及按独立准确率保留历史最佳。 |
| B2 | 与 B0/B1 相同的 Pi 入口和工具契约 | 生产 TaskController 管理候选指纹、防重、历史反馈、受控终止和最佳交付。Pi Durable SQLite 保存原审批、期限、预算和实验状态。 |

B0/B1 共用可信 Python 训练、监督进程握手、独立评分和哈希交付。其原子 JSON 收据供独立判题使用，进程重启后没有装载入口。三组复用相同模型配置、关闭供应商自动重试、禁用内置工具和额外上下文。每轮使用新的 Pi 会话、任务工作区与 Run ID。恢复轮启动新的 Pi 会话，从原任务账本载入状态。受控接口允许合法模型代码、学习率、baseline、独立结果和结束操作。

同一任务固定数据、PyTorch CPU、单线程、训练种子 42、验证脚本、质量门槛及候选搜索范围。Token 准入额度 60,000，任务墙钟 600 秒，执行子进程预算 300 秒。Token 准入用同一估算规则，供应商实际结果用于结算。最多尝试数随任务变化。

B0/B1 在中断 Case 的同一边界终止。任务轴要求成功交付，机制轴检查原额度、授权状态和中断后没有新启动。B2 的恢复还需要一致的 Task ID、审批、截止时间和启动记录前缀。此用例衡量同一任务的恢复能力。各组的模型反馈、历史选优、任务恢复入口有意不同。对照只覆盖 v2 单目标搜索。v3 多保真走单独的固定候选 Case。

## 运行和复核

```powershell
npm run build:offline
npm run check
npm run test:ml
npm run bench:axiom -- --profile mechanisms
npm run bench:axiom -- --profile comparison --phase pilot
npm run bench:axiom -- --profile comparison --phase formal --repeats 3
npm run bench:axiom -- --verify private/axiom-bench/<batch-id>/rep-1/T3-COMP-01
```

`comparison-plan.json` 固定任务身份、顺序、环境及重复次数。每轮轮换组别顺序。每次试验保存 `result.json`、`report.md` 和 `manifest.json`。用量来自 Pi 的模型准入和结算回执，预算拒绝生成的合成中止事件会被排除。独立重载结果与操作、权重和交付清单摘要交叉核对。对配置和源码修改产生的摘要拒绝会保留原记录。

`comparison.json` 按同一任务和组别汇总。失败、超时和未知结果保留在已运行分母。均值和中位数公布有效观测覆盖数，缺失数据保留 `null`。正式试验的失败由报告记录，CLI 退出码用于标识 Runner 是否都产出可判分结果。

对同一任务与组别，记已执行运行次数为 `n`，任务轴通过次数为 `c`。`pass@k = 1 - C(n-c,k)/C(n,k)`，`pass^k = C(c,k)/C(n,k)`。两式描述从已观测结果不放回取样的比例。`k > n` 时输出 `null`。小样本用于描述当前结果。

## 判题与机制故障

任务轴检查独立交付、门槛、有效候选及适用的反馈轮次。机制轴检查原审批、实际启动、账本、预算、操作身份和来源。无交付的安全取消仍能通过机制判题。未知模型请求保留预留，核对用量和外部操作后才能继续。供应商单次实际用量超出准入估算单独记录，超限后继续准入或启动才是相应的机制违规。

| Case | 真实执行或宿主注入 |
| --- | --- |
| T2-POL-01 | 真实 Python 进程留下回执，任务账本缺少对应审批操作 |
| T2-DUR-02 | 相同架构、配置和协议真实训练两次，两个启动记录使用同一指纹 |
| T2-BUD-01 | 准入用尽后宿主绕过预算启动额外训练，判题器从命令预留重算发现超额 |
| T2-EVAL-01 | 修改已交付权重，独立复验或交付哈希核对失败 |
| T2-SEARCH-01 | 在 v3 Proxy 提交后终止，原任务只补做 Full，Smoke 和 Proxy 各只启动一次 |
| T2-SEARCH-02 | 将真实 Proxy 凭证注入正式评价记录，独立 Full 交付仍用于任务轴 |

离线批次目录为 `private/axiom-bench-wp072-verified/`。原 `core` 批次 `badfbed2-5de4-4810-8895-bdb705930977` 的九个 Case 全部符合预期，任务轴 4/9、机制轴 9/9。机制批次 `bda0b5a9-6810-4341-92a5-ab30ccb898ea` 使用真实 Python。独立判题器根据证据将越权、重复、追加训练和 Proxy 注入判为机制失败。损坏交付使两个轴失败。正常 v3 恢复的 Run ID 为 `8a7f8638-a25c-41f6-98fa-38bb8c51021c`。训练步从 102 续算到 182，Smoke、Proxy 各一次，Full 两次包含 baseline。重载得到 Smoke 0.5、Proxy 0.994140625 和交付 Full 0.998046875。后者进入任务轴。

正反例覆盖了四种轴组合。正常 v3 恢复双轴通过，正向未确认请求安全暂停时任务失败、机制通过，真实重复训练时任务通过、机制失败，损坏交付时双轴失败。

## 已知范围

- 任务来自单机 Windows Tiny XOR，使用两个合法起点和三种任务条件。结果只适用于该域和固定训练种子。
- 提供方返回的模型 ID 为 `deepseek/deepseek-flash`。底层权重修订与推理随机种子没有供应商证明。服务端缓存可影响 Token 价格和延迟。
- 三组的任务准入与 Python 进程超时使用相同的 600 秒期限。B2 另有原生主动取消计时器。B0/B1 对已经在途的模型请求由 Runner 的 660 秒总超时兜底。
- 执行子进程耗时含 Python 启动、训练及独立评估的进程等待，无法从中推导硬件 CPU 时间。费用为 Pi 模型目录估算。
- 仓库内的 Holdout 标签表示主机管理的评测边界，资产可由公开源码读到。模型工具没有读取评分器或未开放资产的入口。
- 同一任务按组比较。跨任务的综合胜率与统计显著性留待更大样本和不同领域验证。
